# Project Charter

## 1. Project identity

**Name:** PDF Intelligence Assistant  
**Working description:** Evidence-grounded PDF summarization and question-answering using dual ingestion pipelines and hybrid RAG.  
**Requirements version:** 0.1 — review draft.

## 2. Problem statement

Users need to understand long and technically dense PDFs and ask follow-up questions without manually searching every page. A conventional vector-only PDF chatbot can miss exact identifiers and terminology, may not represent relationships among entities, and can produce answers unsupported by the document. A summary-only parser also cannot reliably answer multi-hop questions about connected concepts.

## 3. Product vision

Provide a document-scoped assistant that converts each uploaded PDF into both searchable passages and a provenance-aware knowledge graph. It returns concise or detailed summaries, answers questions using only selected document evidence, cites the source page(s), and abstains when evidence is missing or ambiguous.

## 4. Goals

- Allow safe PDF upload, validation and ingestion with visible processing status.
- Produce useful document, section and executive summaries.
- Build two independent but provenance-linked knowledge pipelines.
- Combine vector, lexical and graph retrieval for improved evidence recall.
- Ground every factual answer in retrieved PDF evidence and show page references.
- Prevent cross-user/document data leakage and control untrusted document instructions.
- Measure retrieval, answer, citation, guardrail and operational quality before release.
- Support containerized deployment and operational monitoring.

## 5. Non-goals

- Building the Spotify-like web application described in the sample PDF.
- Browsing the public web to fill gaps in an uploaded PDF.
- Treating an LLM-generated entity or relationship as verified fact without source provenance and validation.
- Training a foundation model.
- Guaranteeing zero hallucinations, zero vulnerabilities or perfect OCR. Risks are reduced through measurable controls and testing.
- Enabling arbitrary Cypher or arbitrary code execution generated by the LLM.

## 6. Users and primary workflows

**Primary user:** An authenticated user who uploads, manages and queries their own PDFs.  
**Operational user:** An authorized administrator who monitors processing failures, service health and usage without unrestricted access to document contents by default.

Primary workflow:
1. Sign in and upload a PDF.
2. System validates the file and creates a document record.
3. Extraction and quality checks run; OCR is used only when needed and enabled.
4. Vector/lexical and graph pipelines run independently from the canonical extracted document representation.
5. User sees progress, completion or actionable failure details.
6. User opens the document, requests a summary or asks a question.
7. System retrieves evidence from the selected document scope and displays an answer with page citations.
8. User can inspect cited passages, ask follow-up questions, export results, or delete the document.

## 7. Success measures (proposed release targets)

Targets are initial acceptance thresholds and must be confirmed after baseline measurement on the agreed evaluation set.

- 100% of supported-PDF answer responses either contain traceable page-level evidence or explicitly abstain.
- 0 cross-user or out-of-scope document evidence leaks in the defined isolation tests.
- At least 90% citation page accuracy on the labelled evaluation set.
- At least 85% Recall@5 on the curated retrieval evaluation set.
- At least 90% groundedness/faithfulness pass rate on answerable evaluation questions, judged with a rubric and human spot checks.
- 100% of deliberately unsupported evaluation questions abstain or clearly state that the selected PDF does not provide the answer.
- No critical or high-severity security findings remain open at production release.
- Ingestion failures are observable, attributable to a processing stage, and safely retryable where appropriate.

These are proposed targets, not measured results. Thresholds must be revised based on document types, evaluation volume and observed baseline.

## 8. Constraints

- Reuse the Guru AI technology direction where appropriate: Python 3.12, LangChain, OpenAI GPT-4o-mini, OpenAI embeddings, FAISS, FastAPI and Streamlit.
- Add Neo4j for the knowledge graph and BM25 for lexical retrieval.
- Use the existing `venv312` only after dependency dry-run and conflict review; do not create another virtual environment unless separately approved.
- Keep this project isolated from `guru_ai` and `guru_ai_enhancements`.
- OpenAI API access and Neo4j connectivity require user-managed credentials; credentials must not be committed to source control.

## 9. Deliverables

- Approved requirements, architecture, data model, security and evaluation specifications.
- Implemented application and automated tests (future phase, not part of this pack).
- Sample-document evaluation set and results.
- Docker deployment artifacts and operations runbook (future phase).
- Release evidence and known-issues register (future phase).

## 10. Risks

- PDF layout complexity can reduce extraction fidelity.
- OCR can introduce recognition errors.
- Entity and relation extraction can invent or misclassify relations.
- Graph retrieval can surface a correct entity but an unsupported connection.
- Retrieval fusion can reduce precision if ranking and scope are not calibrated.
- Shared Python dependencies can affect other projects if upgraded without review.
- Production user isolation, retention and privacy requirements need an explicit deployment decision.
